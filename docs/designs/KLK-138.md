## 1. 目的

ムードカラー ジェネレーター（`palette/index.html` v1.2）が出した配色が「その言葉に合っているか」を、
**人間の判定から作った物差し**で自動採点できるようにする。代表語20語の合格範囲をデータとして持ち、
現行版の得点率（ベースライン）を記録する。第2段以降（辞書の作り直し・合成方法・OKLCH 化）の効果は
この物差しで測る。

この段では `palette/index.html` の生成ロジックと辞書を**変えない**。物差しは生成側を読むだけ。

SPEC との関係: `docs/SPEC.md` は palette を参考資料として挙げるだけで、「言葉→色」の要件は無い
（調査 F9）。この設計の正はチケット KLK-138 と判定者の判定・回答（チケットのログ 2026-11-24 18:50／19:00）。

## 2. 現状

**現在のフロー（調査 F1・F3・F4 の要約）:**
```
入力（言葉・スライダー9本・シード）
  → computeBase()      語の色相を円周平均、彩度・明度を平均 → 基準 H/S/L
  → makePatterns(b, seed)  6スキームをシード付き乱数で並べ替え、先頭3つで3案
                           言葉が効くのはメインだけ。サブ・アクセントは色相の幾何で決まる
  → 3案 × {main, sub, accent, bg}（HSL）→ hslToHex で HEX
```

- 1語・スライダー既定・初期シード（73294978）の出力は決定的。初期シードの3案は全語共通で
  「補色ベース／トーン差ベース／類似色ベース」。第2回判定の現行案（G1・G2）32件は現行コードの
  出力と32/32で一致する（調査 F3）→ **第2回の G 案の判定は、現行版を人間が採点した結果として使える。**
- 色の妥当性を測るテストは無い（調査 F5）。色計算は HSL のみ（OKLCH・HSV は無い）。
- 判定データ（第1回のマス判定・第2回〜第3回追加の案の判定・補正 v4）はすべて `tickets/work/KLK-138/`
  にあり、`.gitignore` で Git から除外されている（clone 直後・CI・配布物には無い）。
- 代表語20語のうち16語は辞書にある（対応表は `make_round2.js` の `DICT`）。
  エレガント・かっこいい・スタイリッシュ・ダークの4語は辞書に無い。

## 3. 設計方針

**採用する方針:**

1. **物差しは「データ（Git 側）＋採点ライブラリ（Node）＋薄い CLI とテスト」に分ける。**
   - 合格範囲は `tests/fixtures/klk138/ruler.json`。判定データから**生成スクリプトで機械的に作る**
     （手で書き写さない）。生成スクリプトは `tools/klk138_build_ruler.py`（配布物に入らない場所）。
   - 採点は Node（依存なし）の `tests/site/klk138_ruler.js`。生成側を呼ぶのも Node なので、
     生成→採点を1プロセスで行える。色変換（sRGB→OKLab/OKLCH・HSV・HSL）もここに置く（U10）。
2. **Git 側に置くのは「人間の判定から作った合格範囲」と、採点結果・一致率の数値だけ。**
   マスの ID（例 `pale-210`）と○△、背景の明暗、補正の規則、判定の間を取った閾値と、その根拠
   （回・案ID・補正の版）を置く。判定データの HEX・メモ本文・コメント本文・第2回 E 案・外部の配色・
   カタログ集計・Color Hunt/Coolors の数値・氏名は置かない。
3. **採点（報告）とテストの合否を分ける。** 現行版の得点率がいくつでもテストは赤にならない。
   テストが確かめるのは「物差しが壊れていない」「ベースラインが再現できる」「物差しが人間の判定と
   一致している（データがあるときだけ）」の3つ。
4. **物差しの正しさは人間の判定で確かめる。** 第2回の120案・第3回の18案を物差しで採点し、
   人間の判定との一致率を出す。判定データは Git 外なので、テストは「データが無ければ SKIP」
   （前例 check_klk067 K11）。加えて、一致率の**数値だけ**をベースラインファイルに記録する（両方）。
5. **マスの間の色は「HSL の最寄りマス」で判定する（U8）。** 判定の格子は HSL で定義され、
   生成側も HSL なので、同じ空間で最寄りを取る。無彩色・金属の8マスとは OKLab の距離で比べる（§4.4）。
6. **判定の「仮」の数値は、人間の判定の○側と×／△側の「間（ギャップ）」として記録する（U12）。**
   補正に仮の値があり、それがギャップの内側にあればその値を採る。仮の値が無ければギャップの中点を
   小数2桁で採る。どちらの場合もギャップの両端と、その出どころ（回・案ID）を `ruler.json` に残す。
   後の判定でギャップが狭まったら、値を差し替える。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| テストが `tickets/work/KLK-138/*.json` を直接読んで採点する | clone 直後・CI・配布物で SKIP になり、何も測らない（調査 R2） |
| 合格範囲を手で `ruler.json` に書き写す | 判定データとずれても気づけない。生成スクリプト＋ずれ検査（§4.8 C6）のほうが安全 |
| 採点を Python、生成を Node に分ける | 生成結果を受け渡す中間ファイルが増える。依存なしで1プロセスにできる Node にまとめる |
| マスの間を OKLab の最寄りマスで判定 | 試算で第2回96案との一致（完全一致）が 0.54。HSL 最寄りは 0.56。淡い寒色が「明るいグレー」に吸われやすい |
| マスの間を補間（周囲のマスの判定を重み付け） | ○△の境界が格子に依存する点は変わらず、説明しにくい。最寄りで十分 |
| 現行版の合格率に下限を設けて assert する | 現行版は不合格の語があるので全体が赤になる（調査 R1）。受け入れ条件「既存テストがすべて通る」と衝突 |
| 辞書に無い4語を「クール」「モダン」などの近い語で代わりに採点する | 対応づけは人間の判断が要る。判定者は「新設として追加したい」と回答済み → 次の段で辞書に入れて採点する |
| 判定時の表示条件（面積比 62:23:10:5・文字色）を物差しに入れる | 生成側に文字色の役割が無い（調査 F1）。面積比も役割の重み付けに使える精度の判定が無い。役割ごとの判定に留める |

6. JSON は `ensure_ascii=False`・`indent=2`・キー順固定・配列はソート・末尾改行。時刻は入れない

7. **持ち出し検査（書き出し前に必ず実行）**: 出力文字列に次が含まれたら書かずに終了コード 1。

   - `amendments.json` の `decidedBy` の値（実行時にファイルから読む。**氏名を定数としてコードに書かない**）

### 4.4 色変換とマス判定（U8・U10）

`klk138_ruler.js` に置く関数（すべて純関数）:

```js
hexToRgb(hex) -> [r,g,b] (0..1)
rgbToHsl(rgb) -> [h(0..360), s(0..1), l(0..1)]
rgbToHsv(rgb) -> [h(0..360), s(0..1), v(0..1)]
rgbToOklab(rgb) -> [L, a, b]           // sRGB→線形→LMS→OKLab（Ottosson の係数）
rgbToOklch(rgb) -> [L, C, h(0..360)]
hslToHex(h, s, l) -> '#rrggbb'         // judge.html L143-150 と同じ丸め。マスの代表色を作るのに使う
classify(hex, ruler) -> { cell: 'pale-210' | 'n-white' ..., dist }
```

`classify` の手順:
1. HSL を求める。色相の帯 = `(round(h / 30) mod 12) × 30`。
2. トーン = 9トーンのうち `(s − S_t)² + (w × (l − L_t))²` が最小のもの（`w = grid.toneLightnessWeight = 2`。
   同点は `grid.tones` の並び順で先のもの）。→ 格子マス候補 `{tone}-{hue3桁}`。
3. 無彩色・金属8マスのうち、OKLab のユークリッド距離が最小のもの → 無彩色候補。
4. 格子マス候補の代表色（`hslToHex(hue, S_t, L_t)`）と無彩色候補の、入力色からの OKLab 距離を比べ、
   近いほうを採る（同点は格子マス）。

根拠: 判定の格子は HSL のトーン（S/L）×色相30°で作られ（judge.html L129-134）、生成側も HSL。
同じ空間で最寄りを取るのが判定のときの見え方に最も近い。明度の重み `w=2` は「HSL の彩度は明度の端で
見た目に効きにくい」ため。試算では `w=1` で第2回96案の完全一致 0.50、`w=2`・`w=3` で 0.56（同値）。
**注意: `w` は第2回の判定を見て選んだので、第2回の一致率は完全に独立した検証ではない**（§6 R-A）。
無彩色を OKLab で比べるのは、淡いトーン（pale の OKLCH 彩度は 0.018〜）とアイボリー・チャコール
（0.016〜0.017）の彩度が重なり、彩度のしきい値では分けられないため。

**銀マス `n-silver` の限界（改訂 2026-11-24）:** 判定シートの銀（OKLCH L0.78・C0.010）は、色としては
淡いグレーと区別できない。光沢はグラデーションの見本で示していたが、採点するのは単色だけである。
このため `classify` は淡いグレー（例: シンプルの第2回現行案 G1・G2 のメイン。L0.76・C0.013）を
`n-silver` と判定することがある。**`classify` はこの段では変えない**（`n-silver` を候補に残す）。理由:
- 第1回の各語の銀マスの判定は、範囲（cells）としてそのまま使う。銀を候補から外すと、7語
  （かわいい・やさしい・ナチュラル・ポップ・レトロ・和風・知的。銀×で明るいグレー○か△の語）の判定が
  甘くなる方向に変わる
- 設計を改訂するときの試算では、銀を候補から外すと V-M の隣接一致が 0.917→0.906、逆転が 0.083→0.094 と
  少し悪くなった。主の検証（V-M）を、結果を見てさらに動かすことも避けたい
- 代わりに、「銀であること」に意味を持たせる規則（シンプルの金属の×）からだけ銀を外す（§4.6.2）

cells の語で淡いグレーが銀として採点される件は、既知の限界として §6 R-K に記録する。

### 4.5 「マスで判定する語」（kind = cells）の1案の採点（U9）

入力: 1案 `{bg, main, sub, accent}`（HEX）と文脈 `{age}`（スライダー値/100。既定 0）。

**役割ごとの判定**

| 役割 | 判定 | 値 |
|---|---|---|
| メイン | `ok` のマス、または `okWhen` のマスで `age >= ageMin` | 1 |
| メイン | `maybe` のマス（＝差し色なら可。補正 v3 `semantics.maybe`） | 0.5 |
| メイン | それ以外 | 0 |
| サブ・アクセント | `ok`・`maybe`・`okWhen` のどれかのマス | 1 |
| サブ・アクセント | それ以外 | 0 |
| 背景（bg=light） | OKLCH L >= 0.80 → 1、L < 0.40 → 0、間 → 0.5 | |
| 背景（bg=dark） | OKLCH L <= 0.40 → 1、L > 0.80 → 0、間 → 0.5 | |
| 背景（bg=either） | 常に 1 | |

背景の閾値の根拠: 格子の pale トーンは OKLCH L 0.88〜0.93、dark トーンは 0.27〜0.42。生成側の背景は
0.18〜0.27 と 0.87〜1.00 に分かれ（第2回120案）、0.40・0.80 はどちらにも当たらない間にある（`status: 設計値`）。

**減点**

| 減点 | 検出 | 語ごとの扱い | 強さ |
|---|---|---|---|
| 蛍光色 | HSV で S >= 0.60 かつ V >= 0.90 かつ 色相が 50〜200° または 280〜345°（補正 v3 の仮ルールをそのまま採用。第2回で判定者が蛍光と名指しした色をすべて検出し、ほかに検出された色は1件を除き△×の案で使われていた） | 元気・ポップ = `allow`（数えない）／情熱的な = `accentOnly`（アクセントは数えない）／その他 = `standard` | メインが蛍光 → 案は×。サブ・アクセント・背景の蛍光は1つで○→△、2つ以上で× |

蛍光の「1つで△」の根拠: 第2回でアクセントだけが蛍光の案（さわやか R1・R2、和風 R2）は△、
メインが蛍光の案（さわやか V1、和風 V1、ナチュラル V2、誠実 V2）は×。
鮮やかな暖色の C >= 0.10 は外部照合で使った「鮮やかな暖色」の定義と同じ（暖色相の範囲も同じ）。

**1案の判定（○△×）**

```
mainNeon = メインが蛍光 かつ neonPolicy が allow でない
nNeon    = サブ・アクセント・背景のうち蛍光の数（allow は 0、accentOnly はアクセントを除く）
warm     = warmAccentPolicy が weak かつ アクセントが鮮やかな暖色

× : main == 0 または bg == 0 または mainNeon または nNeon >= 2
○ : main == 1 かつ bg == 1 かつ sub == 1 かつ accent == 1 かつ nNeon == 0 かつ warm == false
△ : それ以外
```

返す値（1案）: `{ verdict: 'ok'|'maybe'|'ng', points, roles: {main:{cell,status}, sub:{...}, accent:{...}, bg:{L,status}}, penalties: ['neon:accent', 'warmAccent', ...] }`

### 4.7 合格率の数え方

- 1案の点: ○=1・△=0.5・×=0（判定者の回答 U2）。
- **語の得点率** = その語の案の点の平均。**語の合格** = 得点率 >= 0.75（`scoring.wordPassMin`）。
  2〜3案なら「×が無く、○が半分以上」とほぼ同じ意味になる（例: ○○△=0.83 合格、○△△=0.67 不合格、
  ○○×=0.67 不合格）。
- **全体の合格率（主の数字）** = 辞書にある16語の全案の点の平均（案の数で重み付け。語ごとの案数は同じ）。
  併せて「合格した語の数 / 16」を出す。
- **辞書に無い4語**（エレガント・かっこいい・スタイリッシュ・ダーク）: 採点できないので
  `status: "辞書なし（新設予定）"`・点は `null`。分母に入れず、別の行に表示する（判定者の回答 U1）。
- **入力条件**
  - 主条件 B0: 1語だけ選ぶ・スライダーすべて 0・その他は既定（表示モード auto、カラー系統・トーン・
    金属なし、同系色・基準色の指定なし）・初期シード 73294978・**3案すべて**。16語×3案=48案。
  - 追加条件 B0-age: かわいいに年代スライダー 40（age=0.4、文脈 age=0.4）。3案。合格率の分母には
    入れず、「かわいい（大人かわいい）」の参考行として出す（補正 v3 の条件つき○を測るため）。
  - 参考条件 B1: シード 1〜32 の固定リスト × 16語 × 3案 = 1,536案。全体の合格率と、**スキーム名ごと**
    （6種）の合格率と出現数を出す。主の数字ではない（初期シードでは6スキーム中3つしか測れないため。調査 R8）。
