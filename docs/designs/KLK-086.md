# [KLK-086] ページ構成の自由化 設計

> このファイルは KLK-086（設計）/ 087（指示書とUI）/ 088（規約とスキル）/ 089（実機検証）/
> 090（出荷整合）の5チケットに共通する設計です。
> おそらく機能実装の**最後の大きな修正**（理恵さん・2026-09-04）。

## 1. 目的

実案件の原稿からモックを組むとき、いまの生成画面では表せないものが2つある。

1. **同じセクションが複数回出るページ**（例: MENU が「ランチ」「ディナー」で2回）
2. **原稿どおりの並び順**（いまは canonical 順固定・案ごとの自動並び替えのみ）

生成指示書に**順序つき・重複あり・個別設定つき**の本文構成（`composition`）を追加し、
SCR-001 をそれを組める UI にする。

## 2. 現状と、着手前に実測した事実

### 2.1 既に複数インスタンス対応ができている層（実測・2026-09-04）

`MENU-01` と `MENU-02` を併置した HTML に対して、**無改修で**次がすべて動いた:

| 部品 | 結果 |
|---|---|
| `ADDR_RE` / 番地書式 | `{KEY}-{NN}` は連番を最初から許容 |
| `list_page_addrs` | `['ABOUT-01','MENU-01','MENU-02']` を正しく列挙 |
| `find_target_section` | MENU-01 / MENU-02 を独立に特定 |
| `read_section_marker(s)` / `pool_for_addr` | `MENU-02` の型読み取り・プール取得 OK（接頭辞で引くため） |
| `is_valid_desired_type` | `MENU-02` への型指定検証 OK |
| `find_quality_warnings` | インスタンス単位で品質検査 OK |
| `GET /sections`・🔄 UI | 実ページから読むので自動対応（KLK-078 の設計が効いた） |

**→ ブリッジ（bridge.py）は変更ゼロで済む。** 変更は「指示書・UI・生成規約・スキル」に閉じる。

### 2.2 変更が要る層

| 層 | 現状 |
|---|---|
| 指示書 `sections` | 重複なし・canonical 順へ正規化（`normalizeSections`）・既定 `["ABOUT","MENU","GALLERY"]` |
| SCR-001 | チェックボックス（選ぶだけ。順序・複数・個別設定なし） |
| 規約 §2/§2.1 | 番地は各 `{KEY}-01` のみ規定。「並び順 v1 は canonical 順」 |
| 規約 §12.1 不変条件⑤ | **3案で並び順が相違**することを要求（check_klk023 S3） |
| 規約 §12.1.2/12.1.3 | 型は「セクション種別 × 案」で一意（インスタンスの概念がない） |
| 規約 §12.2 / §14 | 参考準拠・部分再生成の型決定が KEY 単位 |

## 3. 設計方針

### 3.1 スキーマ — `composition`（additive・version 1 のまま）

```jsonc
{
  "schema": "design-draft-instruction", "version": 1,
  "sections": ["ABOUT", "MENU", "GALLERY", "CTA"],   // 従来どおり併記（互換・派生値）
  "composition": [                                     // ★新規・任意。あるときは本文構成の正
    { "key": "MV" },                                   //   （実際には本文のみ・MVは含めない。下記）
    { "key": "ABOUT", "heading": "私たちについて" },
    { "key": "MENU",  "heading": "ランチ",   "type": "pat-cards" },
    { "key": "CTA" },
    { "key": "MENU",  "heading": "ディナー", "type": "price-table", "moreLink": {"label": "メニュー一覧へ"} },
    { "key": "GALLERY" }
  ]
}
```

- **対象は本文セクションのみ**（NAV/MV/FOOTER は従来どおり自動・固定位置）。
- **エントリの並び ＝ ページの並び**（**全案共通**・理恵さん決定1）。
- 個別設定は既存 `sectionOptions.{KEY}` の語彙をそのまま各エントリへ（§4.2/§4.3 と同じ制約）:
  `heading`（≤40字）・`lead`（≤200字）・`moreLink`（`{label, href?}`）・**`type`**（そのKEYのプール語彙・
  KLK-079 と同じ**許可リスト判定**。CTA/SEARCH は型プールを持たないため指定不可）。
- **`composition` が無い指示書は従来と完全に同じ**（後方互換）。SCR-001 は、構成が既定と等価
  （canonical 順・各1個・個別設定なし）のとき **`composition` を出力しない** → 従来利用の出力はバイト不変。

**上限（理恵さん決定2・CTA修正込み）:**

| 区分 | 上限 |
|---|---|
| 複製可（各≤3個） | ABOUT / MENU / GALLERY / VOICE / FLOW / STAFF / NEWS / PRICE / FAQ / SNS / **CTA** |
| 1個のみ | ACCESS / CONTACT / SEARCH |
| 本文合計 | **12個** |

- **CTA の複数配置**はページ上部・下部に**同一内容**を置く用途（理恵さんの指定）。
  ボタン構成（`sectionOptions.CTA.purpose/buttons`）は**全インスタンス共有**。
  `heading`/`lead` はエントリ単位で変えてよい（共通機構がそのまま効く）。
- **SEARCH** は HERO/NAV への埋め込み（§12.1.3(7)・実体セクションなし）のため、
  **並び順の影響を受けない**。UI では複製・並び替え不可の行として出し、その旨を注記する。

**`sections` との整合**: `sections` ＝ `composition` のキー集合（canonical 順・重複除去）。
SCR-001 は常に両方を整合させて出力する。手編集などで不一致の指示書が来たら、
スキルは**受付チェックで停止**して案内する（曖昧な入力のまま30分の生成を走らせない）。

### 3.2 番地の採番（§2 拡張）

同一 KEY のインスタンスは **composition の出現順に `-01`, `-02`, `-03`**。
既存の1個目はすべて `-01` のまま＝**既存生成物・見本・golden と完全互換**。

### 3.3 型の決め方 — 優先順位を1段拡張（§12.1.x/§12.2/§14 整合）

**生成時（インスタンスごと・強い順）:**

| 順 | 決め手 | 適用範囲 |
|---|---|---|
| 1 | `composition[i].type`（人の指定） | **全案共通**でその型に固定 |
| 2 | §12.2 参考準拠（`thumbnails[0].sectionLayouts`） | 案A・**その KEY の第1インスタンスのみ** |
| 3 | 表引き＋**インスタンス補正**（新設） | 従来の表引き index を k 番目のインスタンスで `(idx + (k-1)) mod 6`。明示指定と衝突したら +1 ずつ送る（決定的・理恵さん決定4） |

- 補正は3案へ同じずらし幅で掛かるため、**案間 distinct（⑥〜⑨）は型未指定の番地では従来どおり成立**する。
- 型を明示した番地は**案間で同一になってよい**（不変条件の条件つき改訂・下記 3.4）。

**部分再生成時（§14 の優先順位・KLK-079 の表に1段挿入）:**

| 順 | 決め手 |
|---|---|
| 1 | `desiredType`（ジョブ仕様＝画面で選んだ型） |
| 2 | **併置 `instruction.json` の `composition` にある当該インスタンスの `type`**（KEY＋出現順で引く） |
| 3 | `data-ref-id` のある案の現行マーカー（§12.2） |
| 4 | 表引き＋インスタンス補正 |

（§14 は既に `instruction.json` を文脈用に読んでいるため、参照先が増えるだけ・決定的なまま）

### 3.4 不変条件の条件つき改訂（§12.1 ①〜⑨）

| 不変条件 | composition 無し | composition あり |
|---|---|---|
| ① `data-columns` 全案同一 | 維持 | 維持 |
| ② セクション集合 全案同一 | 維持 | 維持（**多重集合**として同一） |
| ③ `--m-main` 相違 ④ `data-archetype` 相違 | 維持 | 維持 |
| ⑤ `data-section-order` 案間相違 | 維持 | **全案同一**（並びは人の指定・理恵さん決定1） |
| ⑥〜⑨ 型の案間相違 | 維持 | **`type` 明示のない番地についてのみ**要求 |

`data-section-order` は番地ベース（例 `ABOUT-01,MENU-01,CTA-01,MENU-02,…`）へ拡張。

### 3.5 SCR-001 の UI

「本文コンテンツ構成」をチェックボックスから**ページ構成リスト**へ:

```
┌ ページ構成 ─────────────────────────────┐
│ 1. ABOUT   [設定▾]              [↑][↓][複製][削除] │
│ 2. MENU    [設定▾] 見出し:ランチ  [↑][↓][複製][削除] │
│ 3. CTA     [設定▾]              [↑][↓][複製][削除] │
│ 4. MENU    [設定▾] 見出し:ディナー [↑][↓][複製][削除] │
│ …                                                  │
│ 追加: [ABOUT][MENU][GALLERY][VOICE]…（上限で無効化）│
└──────────────────────────────────────┘
   設定▾ = 見出し / リード文 / 詳細ボタン / レイアウト型（6択＋自動）
```

- 並び替えは **↑↓ ボタン**（ドラッグは実装しない。確実さ優先・JS を薄く保つ）
- 型の選択肢は `SECTION_TYPE_POOLS` と同じ語彙を焼き込み（KLK-078 の写しと同じく、正は規約側）
- 既定状態＝従来（ABOUT/MENU/GALLERY 各1・設定なし）→ `composition` 非出力

## 5. 影響範囲

**変更しない（実測で確認済み）:** `draft-gen/bridge.py` 全体（番地機構・/sections・/regenerate・
desiredType・品質検査・SSRF まわり）・compare.html（実ページから読むため）・palette・カタログ系。

**変更する:** `draft-gen/index.html`（UI・buildInstruction）・DRAFT_RULES（§2/§2.1/§12.1x/§12.2/§14）・
draft-generate SKILL.md・draft-regenerate SKILL.md（優先順位1段）・SPEC・tests。

## 6. リスク

| リスク | 対策 |
|---|---|
| **スキルが composition を無視する**（KLK-072〜076 と同じ形） | KLK-089 で「並び・連番・個別設定が反映されたか」を**実物で機械検査**。`verify-mockup.py` に composition 照合を追加（instruction.json が併置されるので照合可能） |
| 後方互換が壊れる | 既定状態で `composition` 非出力＝**バイト一致**をスモークで固定。既存 golden は全部 composition 無し |
| 12セクション×個別設定で生成が長時間化 | 上限12で抑制。実測を KLK-089 で取り、NFR-001（目安10分）を超えるなら上限を下げる相談 |
| 不変条件の緩和で checker が混乱 | 緩和は「composition あり」に限定し、条件を規約と checker の両方に明記 |
| CTA 複数と §4.4 自動整列の相互作用 | ボタン構成は共有＝整列計算は1回分の再利用。個別見出しのみ可変 |

## 7. マイグレーション戦略

すべて additive。`composition` の無い既存指示書・既存生成物・見本・golden は無変更で動く。
`sectionOptions.{KEY}.heading/lead/moreLink` は**第1インスタンス向けの従来互換**として維持
（composition のエントリ設定が優先）。

## 8. ロールバック戦略

`git revert`（UI・規約・スキル・テストの追加のみ。データ形式の破壊的変更なし）。

## 9. 受け入れ条件（全体）

- [ ] 既定状態の指示書出力が従来と**バイト一致**（後方互換の完全性）

- [ ] 型明示の番地は全案その型・未指定の番地は案間 distinct を維持

- [ ] `verify-mockup.py` が composition との一致を機械検査できる
- [ ] full suite 非回帰／全 checker・全 smoke NG 0本
