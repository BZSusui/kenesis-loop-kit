## 3. 設計方針

### 論点1〜5の確定（investigator が残した設計論点への解）

**採用する方針:**

**① 新フィールドの最終形（キー名・格納形）** — entry 直下に **`sectionLayouts`**（オブジェクト＝map）を任意で追加する。
- 形: `"sectionLayouts": { "SECTION_KEY": "型マーカー", ... }`。**1セクション＝1型**（配列にしない）。参考画像1枚は
  各セクションにつき1レイアウトしか写らないため単一値で足りる。
- キー（SECTION_KEY）: **語彙を持つ7セクションのみ**（`HERO`・`ABOUT`・`MENU`・`GALLERY`・`VOICE`・`FLOW`・`STAFF`）。
  `HERO` は MV/ヒーロー（`.m-hero`・`data-hero`）を指す（§12.1.1 のヘッダ表記に合わせる）。
- 値: DRAFT_RULES §12.1.1/§12.1.2 の型マーカー文字列、または後述の番兵 `"other"`。
- `tags`（配列）への平文混入は**しない**（フィルタ語彙 tags と衝突するため別キーに分離）。

**② 「型なし」の表現** — 3状態を**キーの有無と番兵**で表す（`null` は使わない＝状態を増やさない）。
| 状況 | 表現 |
|---|---|
| そのセクションが画像に無い／未判定 | **キーを省略**（map に載せない） |
| セクションはあるが既存プールに当てはまる型が無い（プール外） | 値 `"other"`（番兵・将来 STEP B の型追加候補シグナル） |
| `sectionLayouts` 自体がまだ無い（既存エントリ） | **フィールドごと省略**（`{}` 空mapも可） |
additive・後方互換に最も有利（未指定＝未判定を許容）。

**③ 語彙の二重管理回避（最重要）** — 型マーカー名の**唯一の正は DRAFT_RULES §12.1.1/§12.1.2**。
CATALOG_RULES.md は**語彙を再掲・複製しない**。既存 CANONICAL_COLORS の原則（CATALOG_RULES.md:5「ずれたら
bridge.py を正とし本ファイルを合わせる」）と同型で、「**値の語彙の正は DRAFT_RULES §12.1.x・乖離時はそちらに
合わせる**」と参照方式で書く。これにより STEP B で型プールが増えても catalog 規約側は**書き換え不要**（受け入れ条件5）。

**④ 型語彙が無い8セクションの扱い** — **提案対象外（キーを設けない）**。将来の予約もしない。
理由: `sectionLayouts` は map なので、STEP B で当該セクションに語彙が付いた時点で**キーを1つ足すだけ**（データ追加）で
追従できる。空の番兵キーを今から予約すると死語彙になり、参照方式（③）の利点を損なう。

**⑤ 機械検証の方針** — **`validate_catalog` に「構造（shape）検証のみ」を additive に足す。値の語彙照合は行わない。**
- present→検証 / absent→OK（KLK-016 と同型の任意検証）。`sectionLayouts` が present なら「オブジェクトであること／
  各値が非空文字列であること」を検証。array や数値・空文字は reject。
- **値の語彙照合（マーカーが §12.1.x に実在するか）は行わない。** 理由: 語彙の正は DRAFT_RULES（markdown）であり
  bridge.py から import できない。bridge.py に語彙表を持たせると DRAFT_RULES・CATALOG_RULES に次ぐ**第3の複製**が生まれ、
  STEP B のたびに手動同期が必要になり受け入れ条件5（追記だけで追従）と論点③に反する。
- 語彙の妥当性（正しいマーカーか）は**品質の問題**として **M群（人間確認ゲート・目視）** で担保する。これは色の
  「7カテゴリ集合メンバーシップは S群／タグ品質は M群」（CATALOG_RULES §2 末尾）と同じ切り分け。色の集合メンバーシップが
  S群なのは CANONICAL_COLORS の**正が bridge.py にある**からで、レイアウト型は**正が DRAFT_RULES にある**ため対称的に
  「機械は shape だけ・語彙は人間」とする。

### 代替案と却下理由
| 案 | 却下理由 |
|---|---|
| 値を配列 `["voice-cards"]` にして複数型許容 | 参考1枚のセクションは1型。配列は空/多重の曖昧さを生み、KLK-031 の表引きが複雑化。1セクション1型が素直 |
| 型なしを `null` で表す | キー省略で十分。`null` を足すと「省略」「null」「other」の3表現になり判定が増える。additive には省略が最有利 |
| 8セクションのキーを予約（`"other"` 固定などで） | 死語彙が増え参照方式の利点を損なう。map なので STEP B でキー追加すれば足りる（予約不要） |
| CATALOG_RULES に型マーカーを再掲（列挙） | STEP B で二重更新が必要（論点③違反）。参照方式なら書き換え不要 |
| `validate_catalog` で語彙メンバーシップ照合（bridge.py に語彙表を持つ） | DRAFT_RULES に次ぐ第3の複製。STEP B のたび手動同期＝受け入れ条件5違反。shape 検証＋人間ゲートで代替 |
| DRAFT_RULES.md をパースして語彙を導出する静的テストを今すぐ追加 | markdown 表パースは脆く、費用対効果が STEP A 段階では低い。将来の任意強化として Open Questions に記録（非ブロッカー） |
| schema/version を上げる | additive（未知フィールド無害・既存検証を壊さない）ゆえ不要。KLK-016 も colors 制約追加で version=1 据置 |

## 4. 実装詳細

### 4-1. catalog.json スキーマ（additive・スキーマ例）

```json
{
  "id": "cat-0001",
  "file": "cat-0001.png",
  "source": "own",
  "colors": ["ゴールド"],
  "sectionLayouts": {
    "HERO": "split",
    "ABOUT": "img-left",
    "GALLERY": "pat-grid",
    "VOICE": "other"
  }
}
```
- `sectionLayouts` は**任意**。省略・`{}`（空map）も有効。
- キーは7セクション（`HERO`/`ABOUT`/`MENU`/`GALLERY`/`VOICE`/`FLOW`/`STAFF`）のみ。値は DRAFT_RULES §12.1.x の
  マーカー文字列、または `"other"`（プール外）。値の**語彙の正は DRAFT_RULES §12.1.1/§12.1.2**（catalog 側は再掲しない）。

### 4-2. `validate_catalog` への追記（bridge.py:455-503・shape 検証のみ・additive）

`colors` 検証ブロックの後（entry ループ内）に、次を追加する（**値の語彙照合はしない**）:
```python
# KLK-030: sectionLayouts(任意)。present→shape検証 / absent→OK。
# 値の語彙の正は DRAFT_RULES §12.1.1/§12.1.2。ここでは語彙照合をしない
# (bridge.py に語彙表を持つと第3の複製になり STEP B 追従性を損なうため)。品質は M群/人間確認ゲート。
sl = entry.get("sectionLayouts")
if sl is not None:
    if not isinstance(sl, dict):
        errors.append("{0}.sectionLayouts はオブジェクト(セクションKEY→型マーカーのmap)ではありません".format(where))
    else:
        for k, v in sl.items():
            if not isinstance(k, str) or not k:
                errors.append("{0}.sectionLayouts に非文字列/空のキーがあります".format(where))
            if not isinstance(v, str) or not v:
                errors.append("{0}.sectionLayouts['{1}'] の値は非空文字列である必要があります".format(where, k))
```
- `validate_catalog` の docstring にも1行追記（sectionLayouts は present のとき object・値は非空文字列を検証、語彙照合はしない旨）。
- `validate_import_request`（POST ボディ検証）は**変更不要**（files 列挙のみを扱う）。

### 4-3. CATALOG_RULES.md への追記（§1 スキーマ表・JSON例・§3 タグ付け規約）

- **§1 JSON例**: 例エントリに `"sectionLayouts": {"HERO":"split","ABOUT":"img-left"}` の行を足す。
- **§1 フィールド定義表**に1行追加:

  | パス | 型・値域 | 必須 | 備考 |
  |---|---|---|---|
  | `entries[].sectionLayouts` | オブジェクト（`"SECTION_KEY":"型マーカー"`）。キーは7セクション（HERO/ABOUT/MENU/GALLERY/VOICE/FLOW/STAFF）・1セクション1型 | - | セクション別レイアウト型。**値の語彙の正は DRAFT_RULES §12.1.1/§12.1.2（ここには再掲しない・乖離時は DRAFT_RULES に合わせる）**。キー省略＝未判定/該当なし、値 `"other"`＝プール外。参考準拠生成（KLK-031）の土台 |

- **§1 `validate_catalog` 説明段落**に追記: 「`sectionLayouts` は present のとき object かつ各値が非空文字列であることを
  構造検証する。**値の語彙照合は行わない**（品質＝正しいマーカーかは M群/人間確認ゲートで担保）」。
- **§3 タグ付け規約に新項目追加**（例文）:
  > - **セクション別レイアウト型**（`sectionLayouts`・任意）: 参考画像に写る各セクションを **DRAFT_RULES §12.1.1/§12.1.2 の型プール**へ寄せ、1セクション1型で提案。対象は語彙を持つ7セクション（HERO/ABOUT/MENU/GALLERY/VOICE/FLOW/STAFF）のみ。**該当セクションが画像に無い/未判定はキーを省略**、**近い型が無い（プール外）は `"other"`**。**型マーカーの語彙は再掲しない（正は DRAFT_RULES §12.1.x・乖離時はそちらに合わせる）**。確定は人間承認後のみ。

### 4-4. SKILL.md への追記（手順2/3/4・してはならないこと）

- **手順2（視覚認識・SKILL.md:50-63）** に推定項目を1つ追加（例文）:
  > - **セクション別レイアウト型**（`sectionLayouts`・任意）: 画像の各セクションを **DRAFT_RULES §12.1.1/§12.1.2 の型プール**へ寄せて1型ずつ提案する（対象は HERO/ABOUT/MENU/GALLERY/VOICE/FLOW/STAFF の7セクションのみ・1セクション1型）。**該当セクションが無い/未判定はキー省略**、**プール外は `"other"`**。**型マーカーは DRAFT_RULES §12.1.x の語彙のみ**（独自語で付けない）。
- **手順3（人間確認・SKILL.md:65-72）**: 他タグと並べて `sectionLayouts` を提示し、修正可・**承認後のみ確定**（自動確定禁止＝既存原則の踏襲）。
- **手順4（確定・SKILL.md:74-82）**: 承認された `sectionLayouts` を entry に書く（省略・`{}`も可）。追記後の `validate_catalog` 相当の自己確認に sectionLayouts の shape も含める。
- **してはならないこと** に2項目追加:
  > - セクション別レイアウト型（`sectionLayouts`）を人間確認なしで自動確定すること。
  > - 型マーカーを DRAFT_RULES §12.1.1/§12.1.2 以外の独自語で付けること（語彙の正は DRAFT_RULES）。

### 4-5. 既存3エントリ（cat-0001〜0003）の再タグ付けの段取り（設計時点で値を確定しない）

**視覚認識と理恵さん確認が要るのは実行フェーズ**（implementer＋人間）。設計は段取りのみ定義する:
1. implementer が `catalog/img/cat-0001.png`〜`cat-0003.png` を **Read で開いて視覚認識**し、各画像に写るセクションを
   §12.1.x の型プールへ寄せて `sectionLayouts` を**提案**（該当なしはキー省略・プール外は `"other"`）。
2. **理恵さんに提案を提示し、確認・修正を受ける**（`/catalog-import` 手順3 と同じ人間確認ゲート）。
3. **承認された値のみ** 該当 entry に `sectionLayouts` を追記し、`generatedAt` を更新。`validate_catalog` の shape を自己確認。
4. これは M群（目視・非決定）に属する作業。**設計時点でタグ値は確定しない**（本設計書に具体値を書かない）。

### 4-6. テスト（機械検証・受け入れ条件を具体化）

`tests/site/check_klk013.py` に **S18・S19** を追加（KLK-016 が S16/S17 を足した先例と同型・source of truth は本設計書 §9）。
`tests/fixtures/klk013/catalog.sample.json` の1エントリに shape 妥当な `sectionLayouts` を足す（既存の架空マーカー
`架空/ダミー/サンプル/デモ/見本` を title/note に保持＝S12 を壊さない）。

- **S18（`validate_catalog`: sectionLayouts の shape 検証）**
  - sectionLayouts 無しの entry → **accept**（後方互換・既存3エントリ相当）
  - `sectionLayouts = {}` → **accept**
  - `sectionLayouts = {"VOICE":"voice-quote-stack","ABOUT":"img-left"}` → **accept**
  - `sectionLayouts = {"VOICE":"other"}` → **accept**（番兵）
  - `sectionLayouts = ["VOICE"]`（配列） → **reject**
  - `sectionLayouts = {"VOICE": 3}`（非文字列値） → **reject**
  - `sectionLayouts = {"VOICE": ""}`（空文字列値） → **reject**
- **S19（ドキュメントの語彙参照方式・自動確定禁止）**
  - CATALOG_RULES.md に `sectionLayouts` フィールド定義があり、値の語彙の正として **`DRAFT_RULES` と `12.1`** を参照する文言を含む（＝参照方式）。
  - SKILL.md 手順2/3 に `sectionLayouts` の提案＋人間確認の記述がある（自動確定しない）。

**回帰**: 既存 full suite（150）が緑のまま（`python3 -m unittest discover -s tests`）。S1-S17 は不変（sectionLayouts 追記は
既存 entry の他フィールド検証に影響しない）。fixture への sectionLayouts 追記後も S6「sample受理」は true のまま。

## 7. マイグレーション戦略

- **schema/version は上げない（version=1 据置）**。`sectionLayouts` は additive な任意フィールドで、未知フィールドを
  拒否しない現行 `validate_catalog` と両立する（KLK-016 が colors 制約を version 据置で追加した先例と同型）。
- 既存3エントリは §4-5 の段取りで段階的に付与（AI提案→理恵さん確認）。**未付与のまま**でも閲覧・ピッカー・検証は動作する
  （後方互換）。データマイグレーションスクリプトは不要。

## 8. ロールバック戦略

コードは additive のみ（`validate_catalog` の shape 検証追加・ドキュメント追記・fixture 追記）。問題時は revert で完全復旧する。
`catalog/catalog.json` はデータ変更のみ（Git 除外のためコミット対象外・手動で該当 entry の `sectionLayouts` を削除すれば戻る）。

```bash
# コミット単位のロールバック（推奨・履歴保持）
git log --oneline
git revert {KLK-030 のコミットハッシュ}
# メッセージにチケットIDを付与: [KLK-030][REVERT] セクション別レイアウト型タグ拡張を取り消し
```
revert 後、`sectionLayouts` を持つ catalog.json は未知フィールドとして無害に無視される（前方互換）。fixture から
sectionLayouts を除けば S18/S19 も消える。
