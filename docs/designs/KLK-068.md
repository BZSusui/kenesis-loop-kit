# [KLK-068] カタログエントリの削除機能 設計

## 1. 目的

誤登録・重複したカタログエントリを**画面から取り消せる**ようにする。
配布先の各メンバーが自分でカタログを育てる以上、**間違いも自分で直せる**必要がある。

## 2. 現状

- 削除系のエンドポイントは**存在しない**（bridge の POST は generate / regenerate / catalog-import /
  upload / catalog-upload / catalog-commit の6つ）。
- 取り消すには `catalog.json` を手で編集し、`catalog/img/` の画像も手で消すしかない。
- 実際に `cat-0054` と `cat-0056` が **バイト単位で同一**の重複として残っている。

## 3. 設計方針

**採用する方針: `POST /catalog-commit` の逆操作として `POST /catalog-delete` を作る。
ただし画像は消さずに `catalog/.trash/` へ退避する。**

### 3.1 なぜ「削除」ではなく「退避」か

`catalog/` は **Git 管理外**（REQ-011）である。つまり **`git revert` で戻せない**。
登録（KLK-064）は間違えても削除すればよいが、**削除を間違えると原本が失われる**。
非対称なリスクなので、`catalog/.trash/{id}.{ext}` へ移すだけにする。

- `.trash/` は `catalog/` 配下なので Git 除外の内側（機密規律を維持）。
- 溜まったら人間が Finder で消せばよい。**自動削除はしない**（それでは退避の意味がない）。
- 画面には「**画像は `catalog/.trash/` に移動します（自動では消えません）**」と明示する。

### 3.2 処理順（`POST /catalog-delete`）

```
① Origin 検証 → 403
② サイズ上限 → 413/400
③ JSON パース → 400
④ 入力検証   ids が配列・各 id が is_safe_catalog_name → 400
⑤ 実在確認   catalog.json に無い id → 404（部分的に無い場合も 404 で全体を拒否）
⑥ 事前検証   削除後の catalog 全体を validate_catalog → 400（**1件も消さない**）
⑦ 画像退避   catalog/img/{file} → catalog/.trash/{file}（失敗しても続行・ログのみ）
⑧ 書き込み   一時ファイル → os.replace で原子的置換
⑨ 200        {deleted, total, ids}
```

- ⑧で失敗したら⑦の退避を巻き戻す（`.trash` → `img`）。**あらゆる例外で巻き戻す**
  （KLK-064 で `except OSError` が狭すぎて中途半端な状態を作った教訓）。
- 削除は `catalog.json` と `catalog/img/` のみを対象とし、他のフォルダには触れない。

### 3.3 画面（SCR-004）

- 各カードに控えめな**🗑 削除**ボタン。
- 押すと**確認モーダル**（KLK-064 の作法を流用）。モーダルには
  **サムネイル・タイトル・id** を出し、「何を消すのか」が目で分かるようにする。
- 「削除する」を押して初めて `POST /catalog-delete`。完了後に一覧と件数を再読込。
- モーダルに「画像は `catalog/.trash/` へ移動します（自動では消えません）」を明記。

**代替案と却下理由:**

| 案 | 却下理由 |
|---|---|
| 画像を実際に削除する | `catalog/` は Git 管理外で復元できない。**削除を間違えると原本が失われる**。登録の誤りより被害が大きく、非対称 |
| `confirm()` で済ませる | 何を消すのか（どの画像か）が分からない。重複が2件並んでいるとき、どちらを消したのか確信が持てない |
| 一括削除を入れる | 誤操作の被害が一気に大きくなる。重複解消は数件の作業であり、1件ずつで足りる。**必要になってから足す** |
| `catalog.json` から消すだけで画像は残す | `catalog/img/` に孤児が溜まり、次の id 採番（`next_catalog_id` は img も見る）に影響する |
| ソフトデリート（`deleted: true` フラグ） | `catalog.json` が肥大し、フィルタ・件数・参考選択のすべてに分岐が増える。退避で足りる |

## 6. リスク

| リスク | 深刻度 | 軽減策 |
|---|---|---|
| 誤操作で実績を失う | **high** | ①画像は消さず `.trash/` へ退避 ②確認モーダルで対象を目視 ③一括削除を入れない |
| `catalog.json` を壊す | **high** | 退避より前に `validate_catalog`／一時ファイル→`os.replace`／失敗時は退避を巻き戻す |
| `catalog/` の外を消す | **high** | 対象は `catalog_img_dir` の `{file}` のみ。`is_safe_catalog_name` と配下確認 |
| `.trash/` が肥大する | low | 自動削除しない方針を明示。人間が判断して消す |
| 孤児画像で id 採番がずれる | low | 退避により `catalog/img/` から消えるので `next_catalog_id` に影響しない |

## 7. マイグレーション戦略

なし（新機能）。`catalog/.trash/` は初回削除時に作成する。

## 8. ロールバック戦略

```bash
git revert {コミットハッシュ}
```
既に退避した画像は `catalog/.trash/` にあるので、必要なら手で `catalog/img/` へ戻し
`catalog.json` にエントリを書き戻す（`.trash/` に残しているのはこのため）。
