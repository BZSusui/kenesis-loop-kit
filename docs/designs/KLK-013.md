## 3. 設計方針

投資家のUnknowns **U-A（JSON読込方式）/ U-B（フォルダ名・スキーマ・取り込みMVP）** と、主配色抽出・REQ-004連携を

### 3.1 U-A JSON読込方式 ＝ ブリッジ配信（同一オリジン）を主線＋file:// フォールバック

**採用: (c) ハイブリッド。委細は「committed 静的シェル＋外部データ」に分離して機密を守る。**

静的HTMLを file:// 直開きすると `fetch` がブラウザに遮断されうる（KLK-010 U-4 の既知制約）。加えて**カタログJSON/画像は
社外秘**（クライアント名を含む）でGit除外フォルダにしか置けない。よって「委細を焼き込んだ単一HTML」を**コミットすると
機密が公開対象に漏れる**。この矛盾を、次の分離で解く。

1. **committed 静的シェル `draft-gen/catalog.html`（機密ゼロ・外部依存ゼロ・SCR-004本体）**
   カタログの実データを一切含まない**アプリの器**。フィルタUI・グリッドの描画ロジック・拡大モーダル・取り込みUIを持ち、
   起動時に**データを外部から読む**。NFR-005（外部CDN依存なし）は満たす（読むのは同一オリジン `/catalog.json` のみ・CDN無し）。
2. **主線＝ブリッジ配信（同一オリジン）**
   ブリッジ稼働時、`GET /catalog` が `draft-gen/catalog.html` を配信し、シェルは `fetch('/catalog.json')`（同一オリジン・
   CORSレス）でデータを、`<img src="/catalog/img/{id}">` で画像を得る。データ・画像はGit除外 `catalog/` から**ブリッジが
   都度読む**ため、committed ファイルに機密が焼き込まれない。
3. **フォールバック＝health-gated グレースフル＋（任意）Git除外のオフラインスナップショット**
   シェルは起動時に `GET /health`（`AbortController` 約800ms）を試行し、成功なら上記主線、失敗（file:// 直開き・ブリッジ
   非稼働）なら**空状態＋起動案内**（「`python3 draft-gen/bridge.py` を起動してください」）を表示して壊れない
   （compare.html の health-gated 作法・KLK-012 と同型）。**committed シェルには機密スナップショットを焼き込まない**。
   純オフライン閲覧が要るときは、`/catalog-import`（またはブリッジ）が**Git除外フォルダ内**に自己完結HTML
   `catalog/catalog.html`（データをインライン・画像を相対 `img/{file}` 参照）を生成する。この生成物は `catalog/` 配下＝
   Git除外なので機密漏洩がなく、file:// で相対画像も読める（同一ディレクトリツリー相対は file:// でも通例可）。

> **なぜインラインスナップショットを committed シェルに焼き込まないか（重要）**: 投資家 (b) 案（HTMLへ焼き込み）を
> committed ファイルで行うと、クライアント名を含むカタログが公開対象に載る（REQ-011/NFR-004 違反）。インライン方式は
> **Git除外フォルダ内の別ファイル `catalog/catalog.html`** としてのみ許可する（漏洩ゼロ＋オフライン可）。

### 3.2 U-B フォルダ名・スキーマ・取り込みMVP

- **フォルダ名＝`catalog/`（Git除外・3ファイル同期）**。KLK-007 の `mockups/` と同じく `.gitignore`・`.gitignore.public`・
  `.gitignore.private` の3ファイル末尾へ `catalog/` を同期追記する（`git check-ignore` で検証）。構成:
  ```
  catalog/
  ├── catalog.json        # カタログ索引(本文の正・社外秘)
  ├── img/                # 実績画像・収集見本の実体(社外秘)  例: cat-0001.jpg
  ├── .pending/           # 取り込みステージング(新規画像のドロップ先・処理前)
  └── catalog.html        # (任意・生成物) オフライン閲覧用スナップショット(データインライン・機密)
  ```
- **カタログJSONスキーマ（§4.1 で全定義）**。1エントリ＝画像id/ファイル名/業種/テイスト/主配色カテゴリ配列/
  own|ref/表示タグ/用途メモ。ワイヤーの `.item`（`.src.own`/`.src.ref`・`.tags`・`.use`）に対応。
- **取り込み＋AI自動タグ付けMVP＝`/catalog-import` スキル（人間確認必須）**。新規画像を `catalog/.pending/` に置く →
  `/catalog-import` が各画像を Read で**視覚認識** → 業種・テイスト・主配色（6カテゴリ）・カラムを**推定** →
  **推定結果を提示して人間が確認・修正** →（承認後のみ）画像を `catalog/img/` へ確定移動＋エントリを `catalog.json` へ追記。
  ワイヤー `.autotag`「登録前に確認・修正できます」/`.edit`「タグを修正」が正。**推測で確定登録しない**（draft-generate の
  「受付チェックを飛ばさない」規律と同型）。
- **ワンクリック取り込み＝ブリッジ `POST /catalog-import`（本チケットに含む・薄い additive）**。KLK-011/012 の
  `POST /regenerate` と同型（Origin403→サイズ→JSON→入力検証→jobId→worker→202）で `/catalog-import` をヘッドレス起動する。
  MVP はスキル手動起動でも成立するが、`is_allowed_origin` 踏襲・パストラバーサル防御を**具体的にテスト可能**にするため
  本チケットで薄く実装する（S群でカバー）。

### 3.3 主配色の抽出方式 ＝ AI視覚推定・6離散カテゴリ（決定論的画素抽出はしない）

PIL 不在・stdlib で JPEG/PNG デコード不可（F5）。SPEC §9・NFR-005 が外部/有料ライブラリを禁止するため、**決定論的な
画素抽出での主配色算出は不可**。ワイヤーの主配色チップは6値の**離散カテゴリ**（`グリーン/ブルー/レッド/ゴールド/
ピンク/モノトーン`）なので、厳密HEXでなく「6カテゴリのどれか」を Claude の視覚推定で付与すれば足りる。品質は非決定的
→ **M群（人間確認）**。決定論テストは「`colors` の各値が許可カテゴリ集合 `CANONICAL_COLORS` に入るか」（スキーマ検証）に
**限定**し、タグ「品質」は決してS群に課さない（恒常失敗を避ける・R-3）。

### 3.4 REQ-004 連携 ＝ 最小連携（導線リンクのみ・実データ供給は別チケット）

`draft-gen/index.html` の参考ピッカー `#thumbs` はダミー6件のハードコード（KLK-006 R3）で、生成指示書の
`references.thumbnails=[{id,label,tags}]` 契約は不変。本チケットは **SCR-004 本体＋取り込みが主眼**なので、REQ-004は
**カタログ導線プレースホルダ（L535「もっと探す→実績カタログを開く(未作成: SCR-004)」）を実SCR-004へ差し替える**最小連携に
留める（§4.7）。カタログ実データを `references.thumbnails` 契約へ供給する統合（業種連動の実カタログ供給）は**別チケット**
（スコープ表「本チケットに含まない・architect判断で調整可」と整合・R-4 で回帰非破壊を担保）。

### 3.5 代替案と却下理由

| 案 | 却下理由 |
|---|---|
| **U-A** committed シェルにカタログJSONをインライン焼き込み（(b)単独） | クライアント名を含む社外秘が公開対象ファイルに載る（REQ-011/NFR-004 違反）。インラインは Git除外フォルダ内 `catalog/catalog.html` のみ許可（§3.1） |
| **U-A** file:// から localhost へ fetch を主線 | file:// オリジンの fetch はブラウザにより全面遮断され不安定。ブリッジ配信の同一オリジンを主線にし file:// は health 失敗→フォールバックで壊れない |
| **U-A** ブリッジ配信のみ（file:// フォールバック無し） | ブリッジ非稼働時に画面が空で終わり NFR-005 の「オフライン表示」思想に反する。空状態＋起動案内＋任意オフラインスナップショットで graceful に |
| **主配色** stdlib/自作デコーダで画素からHEX抽出 | PIL不在・JPEG/PNG は stdlib デコード不可。外部/有料ライブラリ禁止（NFR-005）と両立しない。6離散カテゴリのAI視覚推定が唯一現実的（§3.3） |
| **主配色** 決定論テストでタグ品質を検証 | 生成は非決定的で恒常失敗する。決定論テストはカテゴリ集合の妥当性検証に限定、品質はM群（§3.3・R-3） |
| **取り込み** 推定タグを人間確認なしで自動登録 | ワイヤー「登録前に確認・修正できます」に反し、誤タグ・機密の誤登録リスク。人間承認をゲートにする（§3.2） |
| **フォルダ名** `mockups/` に相乗り | 生成物と実績カタログは寿命・意味が別。`catalog/` を独立に切り、除外規則も独立管理（§3.2） |
| **REQ-004** 本チケットでカタログ実データを参考ピッカーへ供給 | スコープ逸脱。`references.thumbnails` 契約・`#thumbs`・`#thumbFilter` を触ると KLK-006 S群が回帰。最小連携（導線リンク）に留める（§3.4・R-4） |
| **取り込み** ブラウザからの実ファイルアップロード（multipart 受信・保存） | ブラウザfetchでのバイナリ保存はブリッジ複雑化＋機密の取り扱い増。ユーザーが `catalog/.pending/` にファイルを置く運用＋Claude Read が単純・安全（KLK-010 の「ユーザーが明示起動」思想と一致） |

### 4.1 カタログJSONスキーマ（U-B・`catalog/catalog.json`）

```json
{
  "schema": "klk-catalog",
  "version": 1,
  "generatedAt": "2026-07-09T09:00:00.000Z",
  "entries": [
    {
      "id": "cat-0001",
      "file": "cat-0001.jpg",
      "title": "サロン内観サイト",
      "industry": "美容・サロン",
      "taste": "ナチュラル",
      "colors": ["グリーン"],
      "source": "own",
      "columns": "1col",
      "tags": ["美容", "ナチュラル", "グリーン", "1カラム"],
      "note": "落ち着いた内観写真主体。ヘッダ余白広め",
      "addedAt": "2026-07-09T09:00:00.000Z"
    }
  ]
}
```

**フィールド定義:**
| パス | 型・値域 | 対応 | 備考 |
|---|---|---|---|
| `schema` | 固定 `"klk-catalog"` | - | 契約識別子。ブリッジ `validate_catalog` が検証 |
| `version` | 整数 `1` | - | スキーマ版。将来変更時にインクリメント |
| `generatedAt` | ISO8601 | - | 最終更新時刻（`/catalog-import` が更新） |
| `entries[]` | 配列 | REQ-105/106 | カタログ1件＝1エントリ |
| `entries[].id` | string 必須・`^[a-z0-9][a-z0-9._-]*$` | - | 画像id。`/catalog/img/{id}` の照合キー。安全文字集合（`is_safe_catalog_name`） |
| `entries[].file` | string 必須・安全ファイル名（`is_safe_catalog_name`・`..`/絶対パス不可） | REQ-106 | `catalog/img/` 内の実体ファイル名 |
| `entries[].title` | string | REQ-105 | 表示ラベル（`.item .shot` 内・**社外秘可**＝Git除外フォルダのみ） |
| `entries[].industry` | string（自由文字列可） | REQ-105/001 | 業種フィルタのキー。初期候補はワイヤー暫定9業種（OQ-003 は本チケットで確定不要・自由入力可） |
| `entries[].taste` | string（テイスト語彙・単一） | REQ-105/101 | ワイヤー暫定7種（OQ-002 依存だが自由文字列で前進） |
| `entries[].colors` | string配列・各値は `CANONICAL_COLORS` の6カテゴリ | REQ-105 | 主配色（通常1件）。決定論検証＝集合メンバーシップのみ（§3.3） |
| `entries[].source` | `"own"` \| `"ref"` 必須 | REQ-105/NFR-004 | own=自社実績（緑バッジ）・ref=収集見本（橙バッジ・第三者著作物） |
| `entries[].columns` | string（`CANONICAL_COLUMNS` 相当）任意 | REQ-105 | カラム構成ヒント（DRAFT_RULES §8 の6値） |
| `entries[].tags` | string配列 | REQ-105 | 表示用の非正規化タグ（`.item .tags`・キーワード検索対象）。省略時は上記構造値から導出 |
| `entries[].note` | string 任意 | REQ-105/106 | 用途メモ（`.use` 近傍・キーワード検索対象） |
| `entries[].addedAt` | ISO8601 任意 | REQ-106 | 取り込み日時（並び替え「新しい順」用） |

- **`CANONICAL_COLORS = {"グリーン","ブルー","レッド","ゴールド","ピンク","モノトーン"}`**（ワイヤー主配色チップ6値）。
  「ベージュ」「ホワイト」等の微細色はフィルタ対象外＝`tags`/`note` の自由記述に置く（フィルタは6カテゴリで統一）。
- **絞り込み（クライアントJS `filterEntries(entries, sel)`・純関数化）**: `industry`（AND）×`taste`（AND）×`colors`
  （選択色 ∈ `entry.colors` なら合致）× `keyword`（`title`/`industry`/`taste`/`tags`/`note` の部分一致）の **AND** フィルタ。
  各フィルタ行の複数チップは OR（同カテゴリ内）／カテゴリ間は AND。
- **機密規律（NFR-004/REQ-011）**: `title`/`note` はクライアント名を含みうる社外秘 → `catalog.json` は `catalog/` 配下
  （Git除外）にのみ置く。テスト用 `tests/fixtures/klk013/catalog.sample.json` は**架空**（実在案件名を含めない）。

### 4.2 ブリッジ決定論コア純関数（additive・import 単体テスト対象＝S群）

`draft-gen/bridge.py` の先頭純関数群（副作用なし・`if __name__=="__main__"` 分離を維持）に**追加**する。既存純関数
（`validate_instruction`・`is_allowed_origin`・`is_safe_mockups_folder` 等）と `/generate`・`/regenerate` は**変更しない**。

```python
CANONICAL_COLORS = {"グリーン", "ブルー", "レッド", "ゴールド", "ピンク", "モノトーン"}
CATALOG_NAME_RE = re.compile(r"^[A-Za-z0-9][A-Za-z0-9._-]*$")   # id/file の安全文字集合
CATALOG_MIME = {".jpg": "image/jpeg", ".jpeg": "image/jpeg", ".png": "image/png"}

def is_safe_catalog_name(name):
    """catalog/img/{name} の name が安全か(パストラバーサル/注入対策・U-A)。
       CATALOG_NAME_RE 一致・'..' セグメント無し・'/' や '\\' や先頭'.' の危険形を拒否。"""
    return (isinstance(name, str) and bool(CATALOG_NAME_RE.match(name))
            and ".." not in name and "/" not in name and "\\" not in name)

def catalog_content_type(name):
    """拡張子から MIME を返す(未知は 'application/octet-stream')。GET /catalog/img/{name} 用。"""
    _, ext = os.path.splitext(name.lower())
    return CATALOG_MIME.get(ext, "application/octet-stream")

def validate_catalog(obj):
    """カタログJSONを検証する(§4.1・多層防御)。
       schema=='klk-catalog' / version==1 / entries=list / 各 entry の
       id(安全名)・file(安全名)・source∈{own,ref}・colors⊆CANONICAL_COLORS を検証。
       返却: (ok: bool, errors: list[str])。"""

def validate_import_request(obj):
    """POST /catalog-import のボディを検証する(注入対策)。
       想定: {"files": ["a.jpg", ...]}(.pending 内の対象・各 is_safe_catalog_name)
       または {"all": true}(.pending 全件)。安全でなければ (False, errors)。"""

def build_catalog_import_command(pending_spec_path, allow_open=False):
    """/catalog-import のヘッドレス実行コマンド(list・shell=False・最小権限)。
       ['claude','-p', f'/catalog-import {pending_spec_path}',
        '--permission-mode','acceptEdits','--output-format','json']
       ★ build_claude_command/build_regenerate_command と同一方針。危険フラグは決して含めない。"""
```

- `is_safe_catalog_name`／`validate_catalog`／`CANONICAL_COLORS` は S群（S6/S7/S9）で import 単体検証する。
- `build_catalog_import_command` は既存 `build_*_command` と同型（`acceptEdits`＋`--dangerously-*` 非含有＝S群 S11）。

### 4.3 ブリッジ HTTP エンドポイント（additive・§3.1/§3.2）

`do_GET`／`do_POST` のルーティングに**追加**（既存分岐は不変）:

| メソッド/パス | 動作 | レスポンス |
|---|---|---|
| `GET /catalog` | `draft-gen/catalog.html` を配信（同一オリジン・`_serve_index` と同型の別ハンドラ） | 200 text/html（+CORS） |
| `GET /catalog.json` | `catalog/catalog.json` を読み `validate_catalog` に通し配信。不在時は空 `{"schema":"klk-catalog","version":1,"entries":[]}` を 200 で返す（画面は空状態表示） | 200 application/json（+CORS） |
| `GET /catalog/img/{name}` | `name` を `is_safe_catalog_name` で照合（不正 400）→ `catalog/img/{name}` を配信。実在確認（不在 404）。`catalog_content_type` で Content-Type 設定。**`os.path.realpath` で `catalog/img/` 配下に収まることを再確認**（多層防御） | 200 image/*（+CORS） |
| `POST /catalog-import` | body=取り込み指示。防御順①Origin（`is_allowed_origin`・403）②サイズ（`MAX_BODY_BYTES`・413/400）③JSON（400）④`validate_import_request`（400）⑤`catalog/.pending/` 内対象の実在確認（404）⑥jobId 発行→`catalog/.pending/{jobId}.import.json` へ検証済み仕様書出し→worker 起動→202 | 202 `{"jobId":…}`（+CORS） |
| `GET /status/{jobId}` | 既存を流用（取り込みジョブも同じ jobs 管理・state/elapsed/message） | 200（既存フォーマット） |

- **worker `_run_catalog_import_job`**（既存 `_run_regen_job` と同型）: `build_catalog_import_command(pending_spec_path)` を
  `shell=False`・`timeout=BRIDGE_TIMEOUT_SEC` で subprocess 実行。成功後 `catalog/catalog.json` の更新を検知し `state="done"`
  （メッセージに登録件数）。**登録は `/catalog-import` スキル内の人間確認を経る**ため、ワンクリックでも最終確定前に確認ダイアログ
  相当の提示が入る（§4.5・M群 M5 で確認）。失敗/タイムアウトは `state="error"`＋pending クリーンアップ（既存 `_cleanup` 流用）。
- **GET /catalog/img/{name} のパストラバーサル防御**: `is_safe_catalog_name` の文字集合ゲートに加え、`os.path.realpath`
  ベースで最終解決パスが `catalog/img/` 実ディレクトリ配下であることを検証（シンボリックリンク等の保険・多層防御・S群 S9 は
  純関数ゲートを、M群 M6 は実配信の封じ込めを確認）。

### 4.5 `/catalog-import` スキル（REQ-106・AI自動タグ付け＋人間確認）

`.claude/skills/catalog-import/SKILL.md`（YAML `name: catalog-import`／`description`）＋
`templates/CATALOG_RULES.md`（スキーマ＋6色カテゴリ＋タグ付け規約＋機密規律）。`draft-generate`/`draft-regenerate` と
同じ節構成（目的／参照／起動と入力／手順／してはならないこと）。

- **起動と入力**: `/catalog-import`。引数（`$ARGUMENTS`）＝ `catalog/.pending/` 内の対象ファイル名の列挙、または
  ブリッジが渡す**ジョブ仕様パス**（`catalog/.pending/{jobId}.import.json`＝`{"schema":"catalog-import-job","version":1,
  "files":[...]}`）、または未指定時は `catalog/.pending/` 全件。**従来同様のファイルパス受理**で後方互換。
- **手順**:
  1. **受付**: `templates/CATALOG_RULES.md` を全読。対象は `catalog/.pending/` 内の JPG/PNG のみ（安全名を確認）。
  2. **視覚認識**: 各画像を Read で開き、**業種・テイスト・主配色（`CANONICAL_COLORS` の6カテゴリから選ぶ）・カラム構成・
     用途メモ**を推定。主配色は決定論的画素抽出をせず**視覚推定で6カテゴリのいずれか**（§3.3）。own/ref は既定 `own`
     （収集見本は取り込み時に `ref` を明示指定）。
  3. **人間確認（必須ゲート）**: 推定タグを**登録前に提示**し、「この内容で登録／タグを修正／除外」を人間が選べるようにする
     （ワイヤー `.autotag`「登録前に確認・修正できます」）。**確認・承認なしに `catalog.json` へ確定しない**。
  4. **確定**: 承認された分のみ、画像を `catalog/img/{id}.{ext}` へ移動（id は衝突しない連番/一意）＋ `catalog.json` の
     `entries` へ §4.1 準拠のエントリを追記し `generatedAt` を更新。`catalog.json` が無ければ空スキーマから作る。
  5. **（任意）オフラインスナップショット再生成**: 要求時のみ `catalog/catalog.html` を再生成（機密インライン・Git除外内）。
  6. **報告**: 登録件数・付与タグ・保存先（`catalog/`）・除外した画像を非エンジニア向けに提示。
- **してはならないこと**: 実在案件名・顧客名の露出（`catalog/` 外への書き出し禁止）／人間確認を飛ばした自動確定／
  主配色を6カテゴリ外の値で付与／`catalog/` 以外への画像・JSON配置（REQ-011/NFR-004）。

## 7. マイグレーション戦略

**データ移行なし（後方互換）。** 生成指示書スキーマ（KLK-006 §4.4・`version:1`）は不変。ブリッジ拡張は純粋な additive
（新規エンドポイント・新規純関数）で、非稼働時も既存 `/generate`・`/regenerate` の挙動・KLK-006〜012 のゴールデン/テストと
完全互換。`catalog.json` は新規スキーマ（`klk-catalog`/version:1）で、将来変更時は `validate_catalog` で版分岐する。
`catalog/` は新規Git除外フォルダで既存資産に影響しない。

## 8. ロールバック戦略

`git revert` ベース（CLAUDE.md「通常のロールバック」準拠）。変更は新規ファイル（`catalog.html`・スキル・テスト・fixtures）
追加と、`bridge.py`／`index.html`／`.gitignore`／CLAUDE.md への additive 変更に閉じる。後方互換（ブリッジ非稼働＝従来動作）
のため revert しても既存パイプラインは動作する。Phase 単位でコミットを分けるため部分 revert 可。

```bash
git log --oneline
git revert {コミットハッシュ}
# 例: [KLK-013][REVERT] 実績カタログ(SCR-004)の取り消し
```
- revert 時は `catalog.html`・`bridge.py`・スキルを**同一版に揃える**（片側だけ戻すと配信元とシェルの整合が割れる）。
- `catalog/` 配下（画像・JSON・スナップショット）は Git 非管理のため revert 対象外（ローカル手動削除）。
- ロールバック時はチケットを done/→active/ へ戻し status を `implementation_done` にしてログへ理由を追記（CLAUDE.md 準拠）。
