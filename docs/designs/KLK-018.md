# [KLK-018] ブリッジが生成成功を「終了コードのみ」で判定し誤って失敗表示するバグ 設計

> このファイルはarchitectが生成・更新するチケット単位の設計書です。
> チケット KLK-018 に対応します。implementer・tester・reviewerが参照します。
> 1チケット = 1ファイル（`docs/designs/KLK-018.md` が常に現行）。改訂時は本ファイルを上書きし、
> チケットのログに改訂理由を残す。過去の設計はGitヒストリで追える（status等の状態は持たせない）。

## 1. 目的

ローカルブリッジ（`draft-gen/bridge.py`）が `claude -p` の**終了コードだけ**で成否を判定するため、
**生成物が全て揃っている（成功している）のに `returncode != 0` で誤って「失敗」と表示する**バグを直す
（KLK-010〜014 のブリッジ資産の堅牢化・additive・ロジック最小変更）。あわせて失敗時のエラー文に
claude の生JSON（使用量・コスト等）断片が露出する問題を、利用者に分かる日本語要約へ置換する。

- **核心:** 終了コードに依存せず「**成果物の存在／更新**」を主判定にする。`returncode != 0` **かつ** 成果物なし
  のときだけ失敗とし、成果物があれば `returncode` を問わず成功パスへ合流させる。
- 同型のバグが3処理（生成 L503 / 再生成 L573 / カタログ取り込み L651）にあるため、**方針を統一**して修正する。
- timeout・起動失敗（claude 不在）は生成物と無関係な独立失敗理由のため**温存**（回帰防止）。

## 2. 現状

KLK-010/011 で **ローカルブリッジ**（127.0.0.1 限定・`claude -p` ヘッドレス・Origin検証・サイズ上限・保存先日付整合）、
KLK-012 で **部分再生成 `POST /regenerate`**、KLK-013 で **カタログ取り込み `POST /catalog-import`**、
KLK-014 で **フォールバック文言・`showBridgeError`** が完成している。3処理のワーカーはいずれも
`subprocess.run(...)` の直後に `if proc.returncode != 0:` の1行だけで失敗を確定し、
`(proc.stderr or proc.stdout or "").strip()[-400:]`（＝claude の `--output-format json` の生JSON末尾400字）を
message へ連結してブラウザに返している。**成果物（生成物）の存在は一切確認していない。**

**現在のフロー（3処理とも同型・investigator §1 確定）:**
```
worker(_run_job / _run_regen_job / _run_catalog_import_job):
  proc = subprocess.run(build_*_command(...), cwd=root, timeout=BRIDGE_TIMEOUT_SEC)
    ├─ except TimeoutExpired → state="error"（タイムアウト文言）→ cleanup → return   ← 温存すべき独立失敗
    └─ except Exception      → state="error"（起動失敗文言）    → cleanup → return   ← 温存すべき独立失敗
  if proc.returncode != 0:                         ← ★バグ: 終了コード単独判定
      tail = (stderr or stdout)[-400:]             ← ★バグ: 生JSON露出
      state="error"; message="…に失敗しました。{tail}" → cleanup → return
  # 成功パス（成果物パス構築・open・state="done"・成功文言）
```

**関連する既存ファイル:**
- `draft-gen/bridge.py`（本チケットで**変更**。純関数 `is_job_success` を additive 追加＋3ワーカーの判定分岐を置換＋失敗message日本語化）
- `draft-gen/index.html`（**変更なし**。`showBridgeError`（L885・KLK-014）は `'エラー：'+msg` をそのまま表示するため、
  bridge が返す message を日本語要約にすれば UI 変更ゼロで是正できる＝investigator §5 確認）
- 既存純関数（流用・副作用なし・S群対象）: `build_folder`(L129) / `select_open_target`(L134) / `resolve_target_html`(L222) /
  `repo_root`(L444)、および `_count_entries`（`_run_catalog_import_job` 内クロージャ L616）
- 前例設計: `docs/designs/KLK-011.md`（S14/S15・bridge ハードニング）・`KLK-012.md`（S群の書き方・live防御テスト）

## 3. 設計方針

**採用する方針（investigator の Unknowns U1〜U5 を確定）:**

### 3.1 成功判定の統一（判定の中核＝純関数 `is_job_success`）
終了コードに依存しない単一の決定関数を新設し、3処理すべてが共有する。**成果物の有無を優先**する:

```python
def is_job_success(returncode, artifact_ok):
    """終了コードに依存しない成否判定(KLK-018)。副作用なし・S群 import 対象。
    成果物(artifact_ok=True)があれば returncode を問わず成功。無ければ returncode==0 のときのみ成功。
    ＝「returncode!=0 かつ 成果物なし」だけを失敗とする(成果物ありを優先)。
    timeout・起動失敗は本関数の手前で独立に失敗確定させる(温存)。"""
    return bool(artifact_ok) or returncode == 0
```

真理値表（S群 S1 で決定論検証する単位）:

| returncode | artifact_ok | 結果 | 意味 |
|---|---|---|---|
| 0 | False | 成功 | 後方互換（従来の returncode==0 成功をそのまま維持） |
| 0 | True | 成功 | 通常成功 |
| **非0** | **True** | **成功** | ★本修正（生成物ありなら exit 非0でも成功） |
| **非0** | **False** | **失敗** | 真の失敗（従来どおり失敗表示を維持） |

3処理は「`artifact_ok`（成果物あり）の**計算方法**」だけが異なる:

- **U1 生成 `_run_job`＝表示物の存在を主判定（採用）。** 既存 L513-516 の決定論パス構築
  （`started_at.strftime` → `build_folder` → `select_open_target` → `abs_target`）を**失敗判定より前へ移動**し、
  `artifact_ok = os.path.exists(abs_target)`（variants>=2 → `compare.html`／==1 → `index.html`）とする。
  「variants 数だけ index ファイルが揃うか」までは見ない（variant列挙の純関数が現状無く、表示物1枚の存在で受入条件を満たす＝
  investigator 推奨。堅牢さと単純さのバランス）。
- **U2 再生成 `_run_regen_job`＝対象の更新検知（mtime 比較）を主判定（採用）。** 上書き方式のため「新規出現」では測れない。
  `artifact_ok = os.path.isfile(abs_target) and os.path.getmtime(abs_target) >= started_at.timestamp() - MTIME_TOLERANCE_SEC`
  とする（`abs_target = os.path.join(root, target)`、`target` は呼出元 `_regenerate` が `resolve_target_html` で構築済み・
  引数で受領）。`OSError` 時は `False`。**時刻の扱い:** `started_at` は `datetime.datetime.now()`（naive local）で、
  `started_at.timestamp()` は epoch 秒（float）に正規化される。`os.path.getmtime` も epoch 秒（float）＝**同一尺度で比較可能**。
  端数対策として `MTIME_TOLERANCE_SEC`（新規定数・`= 2.0`）を許容差に用い、mtime を秒単位に切り詰めるファイルシステムでも
  取りこぼさない（再生成は started_at の後に多分〜数分かけて上書きするため、正常時 mtime は started_at より十分後。
  許容差2秒は誤検知しない）。**`_now().strftime` は新規導入しない（S14 維持）。**`started_at.timestamp()` は strftime ではなく
  epoch 変換であり S14 に非抵触。生成の folder 導出は従来どおり `started_at.strftime` を維持。
- **U3 カタログ取り込み `_run_catalog_import_job`＝`catalog.json` 可読（`after is not None`）を主判定（採用）。** 既存の
  `_count_entries()`（実行後 `after`）を判定へ昇格し、`artifact_ok = (after is not None)` とする。人間確認で0件承認＝件数不変
  （`after == before`）でも正常系のため、`after >= before` ではなく **`after is not None`（catalog.json が読める）** を主判定にする
  （investigator 推奨・堅牢）。`after` の算出を失敗判定より前へ移動する。成功時の件数メッセージ（`after >= before`）は現状維持。

### 3.2 判定順序（回帰防止・investigator §5）
各ワーカーで **timeout 分岐（L486/556/634）と起動失敗 `except`（L496/566/644）は温存**（生成物と無関係な独立失敗理由。
ここを触ると「claude不在で黙って成功扱い」等の重大回帰）。その後、成果物を計算してから決定する:

```
1. except TimeoutExpired → state="error"（タイムアウト文言・現状維持） return   ← 温存
2. except Exception      → state="error"（起動失敗文言・現状維持）    return   ← 温存
3. 成果物パス／成果物有無を計算（生成: abs_target を先に構築 / 再生成: mtime / 取込: after）
4. if not is_job_success(proc.returncode, artifact_ok):
       （診断ログを stderr へ・任意）→ state="error"（日本語要約・下記）→ cleanup → return
5. 成功パス（従来どおり: 成果物を開く・state="done"・成功文言）  ← 成果物あり優先で合流
```

### 3.3 失敗メッセージの日本語化（受入2・§3.1 の失敗時のみ）
`is_job_success` が偽（＝非0かつ成果物なし）のときの message を、claude の stdout/stderr 生JSON を**一切含まない確定文字列**にする。
`tail = (...)[-400:]` の連結を除去する。3処理の**確定メッセージ**:

| # | 処理 | 失敗時 message（確定・生JSON非露出） |
|---|---|---|
| 1 | 生成 `_run_job` | `生成できませんでした。もう一度お試しください。解決しない場合は Claude Code（claude）が起動しているかご確認ください` |
| 2 | 再生成 `_run_regen_job` | `再生成できませんでした。もう一度お試しください。解決しない場合は Claude Code（claude）が起動しているかご確認ください` |
| 3 | カタログ取り込み `_run_catalog_import_job` | `取り込みできませんでした。もう一度お試しください。解決しない場合は Claude Code（claude）が起動しているかご確認ください` |

- **診断ログ（任意・ブラウザには出さない）:** 原因調査の手がかりを失わないため、失敗時に `proc.returncode` と `tail` を
  **`sys.stderr`（サーバコンソール）へ `print(..., file=sys.stderr)` で残してよい**。これはブラウザの message には載せない
  （利用者にはクリーンな日本語要約のみ）。stderr 診断は S群のmessage検査対象外。**採用は任意**（実装判断）。
- **JSONパース（`is_error`/`subtype`）補助判定は不採用（U4）。** 外部CLIのJSONスキーマはバージョン差で変わり得るため、
  成果物存在を主判定にする方針で十分。JSON露出の是正は「stdout を message に載せない（日本語要約へ置換）」だけで達成できる。

### 3.4 成功時の扱い（§3.1 の成功パス合流・受入・investigator U1〜U3）
`returncode != 0` でも成果物ありで成功と判定した場合も、**既存の成功パスへそのまま合流**する
（生成/再生成: 表示物を `build_open_command` で開く・`state="done"`・成功文言 `…が完了しました。{open_target} を開きました`／
取込: `state="done"`・件数メッセージ）。UI（`showBridgeDone`/`showBridgeError`・KLK-014）への影響はゼロ。部分的な exit 非0 は
診断ログ（stderr・任意）へ残すだけで、利用者向けには done として扱う。

**代替案と却下理由:**
| 案 | 却下理由 |
|---|---|
| U1 variants 数の index ファイル一致まで検証 | variant列挙の純関数が現状無く新設が必要。表示物1枚（compare/index）の存在で受入条件を満たす。過剰実装 |
| U2 再生成を `os.path.isfile(target)` の存在のみで判定 | 上書き方式では「対象が消えていない＝最低限」しか測れず、claude が何もせず終わっても成功扱いになりうる。mtime 比較が更新を本質的に捉える |
| U3 取込を `after >= before` で判定 | 人間確認で0件承認（件数不変）＝正常系を失敗にしてしまう。`after is not None`（catalog.json 可読）が堅牢 |
| U4 claude JSON の `is_error` を主判定 | 外部CLIのJSONスキーマはバージョン差で変わり得る（現に exit≠0 でも `terminal_reason:"completed"`）。成果物存在が最も堅牢 |
| 終了コード判定を単純除去（常に成果物のみで判定） | timeout/起動失敗（成果物なし）を拾えず「claude不在で黙って成功扱い」の重大回帰。`returncode!=0 かつ 成果物なし → 失敗` の2分岐が必須 |
| index.html 側でJSON除去 | bridge が既にクリーンな日本語 message を返せば UI 変更不要。触る面を最小化（bridge 単一修正） |
