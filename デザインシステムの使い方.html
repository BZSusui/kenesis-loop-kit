デザインシステムの使い方

公共サイトの作法にのっとってUIを作るための資料が、このキットに入っています。ここでは、その引き方と守り方を説明します。デザインのたたき台を3案作るモック生成システムについては、別冊の 使い方マニュアル.html をご覧ください。

デザインシステムって何ですか

言葉は少し大げさですが、中身は「作り方の決めごとを書いた資料集」です。ボタンはどのくらいの大きさなら押しやすいか、文字と背景はどれだけ明暗を離せば読めるか、入力欄でエラーが出たときは何を見せるか——これまで経験と勘で決めていたことが、読める文章になっている、と思ってください。

このキットに入っているのは、デジタル庁が公開しているデジタル庁デザインシステムのドキュメントです。頭文字をとって DADS と呼ばれます。国の行政サービスのために作られたものですが、条件を守れば誰でも使えます。UIの部品は49種類ぶん収録されていて、ボタン、入力欄、チェックボックス、モーダル、テーブル、カードといった、だいたいの画面に出てくるものは揃っています。

使うと何がうれしいか。大きく3つあります。

  • 「なぜこうしたか」を説明できます。感覚で決めた話ではなく「この基準に沿っています」と言えるので、社内のレビューでもクライアントへの提案でも通りが違います
  • アクセシビリティの配慮が最初から入っています。見えにくい方、キーボードだけで操作する方への対応は、あとから足そうとすると作り直しになりがちです。最初から織り込まれているのは、地味ですがかなり効きます
  • 公共系の案件で共通言語になります。発注側も同じ資料を見ているので、話が早いです

なぜキットに入っているのか

正直にお話しすると、この導入は一度失敗しています。別の環境で組み込もうとしたところ、モック生成システムの配色設定とぶつかってしまい、いったん取り消しました。

原因ははっきりしていて、ワイヤーフレームの生成ルールにDADSの決めごとを混ぜてしまったことでした。生成ルールのほうは独自の配色の決まりを持っているので、そこへ別の基準が入り込むと、どちらが正しいのか分からなくなります。

そこで入れ直すときは、置き場所も役割もきっぱり分けることにしました。DADSは「実際に作るUIの基準」として設計・実装・レビューの工程だけが参照し、モック生成には一切関わりません。くわしくは次の節で説明します。

入っているもの・入っていないもの

ここが最初のつまずきポイントなので、先にお伝えします。

探しているものあるかどこに
部品の用途・構造・状態・アクセシビリティ要件あるcomponents/{部品名}/index.md
色の考え方と、明暗差の下限あるfoundations/color/index.md
余白の組み方あるfoundations/spacing/index.md
色のコード（#0f41af のような値）ないFigmaやコードスニペット側（このキットには未収録）
フォントの実ファイルない別途調達
そのまま貼れる実装コードないコードスニペット側（同上）
「DADSの青って何番ですか」には答えがありません 資料の中に色のコードは書かれていません。書かれているのは「本文と背景は4.5:1以上の明暗差をつけてください」という条件のほうです。色そのものは案件ごとに決めて、条件を満たしているかを測って確かめる、という使い方になります。やり方は色の決め方にまとめました。

ですので、設計書やコードに「DADSが定める色 #xxxxxx」と書いてしまうのは間違いです。そんな値はどこにも書かれていないので、書いた時点で事実と違うことになります。レビューでも見られる項目です。

▲

モック生成とは別物です

このキットには、性格の違う2つの仕組みが同居しています。どちらも「デザイン」にまつわる話なので、念のためはっきり分けておきます。

混ぜると、前回と同じことが起きます。そこで、うっかり混ざらないように機械的な見張りを付けました。生成システム側のファイル（draft-gen/・palette/・生成スキル・見本）に「デジタル庁」「DADS」「design-system」という文字が入り込むと、テストが落ちます。

モック生成画面にこのマニュアルへのリンクを置いていない理由 いま書いた見張りに引っかかる、というのもありますが、それ以前に、リンクがあると「モック生成もDADSに準拠しているんだ」と受け取られてしまいます。実際には準拠していません。誤解のもとになるので、あえて置いていません。

どこに何があるか

資料はぜんぶ docs/design-system/ の中です。

docs/design-system/
├ MANIFEST.md          ← 目次。まずここを見ます
├ _REFERENCE_GUIDE.md  ← 引き方の案内。49種の一覧つき
├ _ATTRIBUTION.md      ← 出典・ライセンス・更新手順
├ components/          ← UIの部品 49種（ボタン、入力欄、テーブル…）
├ foundations/         ← 色・余白・文字・レイアウトなどの土台
├ guidance/            ← 考え方、ロール別の使い方
├ introduction/        ← はじめに、利用条件
└ webaccessibility/    ← アクセシビリティ試験の実施例

ファイルは全部で127個あります。うち125個がデジタル庁の配布物そのままで、_ で始まる2つだけがこのキット側で足した案内です。中身に手は加えていません。

目次にあたるのが MANIFEST.md です。日本語のタイトルと一行説明つきで全ファイルが並んでいるので、「探している部品がどのファイルか」はここを見ればわかります。部品名がうろ覚えでも、_REFERENCE_GUIDE.md に49種の一覧（日本語名とパス）があるので、そちらでも引けます。

Claude Code への頼み方

いちばん簡単なのは、作業を頼むときに一行足すことです。

UIは docs/design-system/ の仕様に従ってください。

これだけで、Claude Code は目次を見て、必要なところだけを読みにいきます。

もう少し具体的に、ファイルまで指定すると精度が上がります。こんな頼み方です。

docs/design-system/components/button/index.md の仕様に従って、
プライマリー・セカンダリー・テキストの3種類のボタンを作ってください。
この問い合わせフォームを、input-text と radio と select の仕様に
合わせて直してください。参照したパスも書き残してください。
いまの画面の配色が、DADSの下限（本文4.5:1・枠線3:1）を
満たしているか測って教えてください。
「全部読んで」とは頼まないでください 125ファイルあります。全部読ませると時間がかかるうえに、いま作っている画面と関係のない仕様まで判断材料に混ざって、かえって精度が落ちます。作る画面に出てくる部品のぶんだけ——だいたい1〜5ファイルで足ります。

部品の名前が分からないときは、探すところから頼んで構いません。「入力フォームに使えそうな部品を MANIFEST.md から探して」と言えば、目次を見て候補を出してくれます。

開発ループの中では

毎回自分で指示を出さなくても、開発ループを回せば、3つの役割が自動でDADSを見にいきます。

  • architect（設計）は、その画面に出てくる部品を決めて、参照したファイルのパスを設計書に書きます。受け入れ条件にも「本文と背景の明暗差が4.5:1以上」のような、あとから測れる形の条件を入れます
  • implementer（実装）は、設計書に書かれたパスを開いて、そのとおりに作ります
  • reviewer（レビュー）は、仕様どおりか、明暗差は足りているか、出典が書いてあるかを見ます

この3つの役割の定義ファイル（agents/architect.md など）に、それぞれ見るべきところが書き込んであります。ふだんは意識しなくて大丈夫です。

数字で決まっていること

資料の中でも、数字ではっきり決まっているものは覚えてしまったほうが早いです。この5つを押さえておけば、たいていの場面は乗り切れます。

対象基準書いてある場所
ボタンなどの押せる範囲44 CSS px 以上components/button/index.md
本文の文字と背景明暗差 4.5:1 以上foundations/color/index.md
枠線・区切り線など文字でない部分隣の色と 3:1 以上同上
フォーカスの枠黄色と黒の2重。変更しない同上
余白基準単位を決めて、その倍数で組むfoundations/spacing/index.md

押せる範囲は44px（見た目の大きさとは別の話です）

指で押すことを考えた最低ラインです。ボタンの見た目が小さくても構いません。小さいサイズのときは上下に余白を足して、指が当たる範囲として44pxを確保すればよい、という考え方になっています。「小さいボタンは作れない」という意味ではないので、そこは誤解しないでください。

明暗差 4.5:1

文字が読めるかどうかの最低ラインです。薄いグレーの文字が読みにくいのは誰でも経験があると思いますが、それを感覚ではなく数値で判定します。測り方は色の決め方に書きました。

フォーカスの枠は変えない

キーボードの Tab キーで操作している人が、「いま自分がどこにいるか」を見失わないための枠です。黄色と黒の二重になっているのは、背景が明るくても暗くても、どちらかが必ず見えるようにするためです。資料には「いかなる場合も変更してはいけない」とはっきり書かれています。デザインの都合で消したり、色を変えたりしないでください。

下のボタンを Tab キーで選んでみてください。二重の枠が出ます。

この見本の色について 青（#0f41af）はこのマニュアル用にこちらで決めた色で、DADSが定めた色ではありません（そもそも資料に色の値はありません）。白いラベルとの明暗差を測ると8.77:1で、下限の4.5:1を満たしています——という、まさに色の決め方のとおりに決めた値です。

余白は「基準を決めて、その倍数で」

まず基準となる単位をひとつ決めて、あとはその倍率で余白を組みます。資料では、よく使われる基準として8 CSS pxが挙げられています。段階は3〜5個くらいに絞ると画面全体がそろって見えます。たとえば8px・24px・64pxの3段階、といった具合です。数字を都度その場で決めていくと、似ているけれど微妙に違う余白が散らばって、締まりのない画面になります。

色の決め方

色のコードは資料にないので、自分たちで決めます。手順はこうです。

  1. 案件の都合で色を決めます。ブランドカラーがあればそれが出発点です
  2. 組み合わせの明暗差（コントラスト比）を測ります
  3. 下限を下回っていたら、明るさを調整してもう一度測ります
  4. 決まった値と、測った数値を設計書に残します

4番目が地味ですが大事です。「この色にした理由」が残っていると、あとから「なぜ？」と聞かれたときに答えられますし、色を変えたい話が出たときの判断も早くなります。逆にここが空白だと、次に触る人が最初から測り直すことになります。

明暗差の計算は手でやるものではないので、Claude Code に頼んでください。

背景 #ffffff に文字 #0f41af を置いたときのコントラスト比を計算して、
DADSの下限（本文4.5:1）を満たしているか教えてください。

だいたいの感覚として、白背景に濃い色ならまず問題ありません。危ないのは、薄いグレーの補助テキスト、色つき背景に白抜き文字、そして枠線だけで区切っているところです。この3つは測る前から怪しいと思っておくとよいです。

出典を書く

DADSを参照して作ったものには、出典を書く必要があります。お願いではなく、デジタル庁が定めた利用条件です。忘れやすいところなので、レビューでも見ています。

書く文はこれです。

出典：デジタル庁デザインシステムウェブサイト https://design.digital.go.jp/dads/

書かれていることをそのまま使うのではなく、案件向けに調整した場合は、「デジタル庁デザインシステムウェブサイトのコンテンツを加工して作成」という旨も併せて書きます。そして、デジタル庁が作ったもののように見せることは禁止されています。ここは踏み外すと面倒なことになるので、迷ったら加工した旨まで書いておくほうが安全です。

どこに書くかは決めてあります。

成果物書く場所
docs/SPEC.mdセクション10（参考資料）
docs/designs/{ID}.mdProposed Design に、参照パスと一緒に
実装コードファイル冒頭のコメント、または README／NOTICE にまとめて

正確な条件はデジタル庁の原文（docs/design-system/introduction/notices/index.md）にあります。キット側での運用のまとめは docs/design-system/_ATTRIBUTION.md です。

新しい版が出たら

DADSはβ版で、いまも更新が続いています。入っているのは v2.17.1（2026年8月19日に取得したもの）です。新しい版に差し替えるときは、こうします。

  1. デジタル庁のリソースページから最新のMarkdownのZIPを取得します
  2. docs/design-system/ の中身を差し替えます。_ で始まる2つのファイルは残してください
  3. _ATTRIBUTION.md のバージョン・取得したZIP・配置日を書き換えます
  4. updates/ の更新履歴を読んで、すでに書いた設計書に影響が出ていないか確認します
部品の名前が変わることがあります たとえば v2.17.1 では「パンくずリスト」が「パンくずナビゲーション」に変わりました。設計書に古い名前で書いてあると、あとで探せなくなります。差し替えたあとに updates/ をひととおり見ておくのは、そのためです。
▲

こわれていないか確かめる

何かを触ったあとで不安になったら、これを実行してください。

python3 tests/site/check_klk111.py

見ているのは大きく4点です。49種の部品がそろっているか、目次のリンクが全部つながるか、モック生成側にDADSが混ざっていないか、配布用パッケージに出典ごと入るか。最後に 0 failed と出れば大丈夫です。

どこかが FAIL になったら、その行に何が起きたかが書かれています。読んでもピンとこないときは、その出力をそのまま Claude Code に貼って「これを直して」と頼んでください。

よくあるつまずき

「DADSの青は何番ですか」と聞かれた

決まっていません。資料にあるのは明暗差の下限だけです。案件ごとに色を決めて、測って、記録します。→ 色の決め方

読み込みに時間がかかる／回答がぼんやりしている

全件読ませている可能性が高いです。「デザインシステムを全部読んで」ではなく、「button と input-text の仕様に従って」のように、部品を名指しで頼んでください。1〜5ファイルで足ります。

モック生成の配色にもDADSを反映させたい

いまの仕組みでは反映されません。意図的にそうしています。どうしても必要になったら、既存の見本とテストを壊さない形で、別のチケットとして慎重に進めてください。思いつきで生成ルールに書き足すと、前回と同じことが起きます。

作りたい部品が49種の中にない

その場合は foundations/（色・余白・文字・レイアウトなど）の考え方だけを借りて自作します。似ている部品があれば、状態の持たせ方やキーボード操作の作法はそこから拝借できます。出典表記は同じように必要です。

部品の名前が資料と食い違っている

改訂で名前が変わったのだと思います。正しいのは MANIFEST.md と、各部品の changelog.md のほうです。

結局どこから見ればいいか分からない

docs/design-system/_REFERENCE_GUIDE.md を開いてください。目的別にどのファイルを見ればいいかの対応表と、49種の一覧が載っています。迷ったときの入口はここです。
